## 0. Method, evidence, and what I could not check

This audit is based on reading the committed source. Findings are labelled by evidence:

- **[VERIFIED]** — read directly in the code; file and line cited.
- **[INFERRED]** — follows from verified code plus documented platform behaviour (e.g. Supabase
  PostgREST defaults), but not executed against a live system.
- **[ASSUMPTION]** — stated belief I could not test.

**What I could not check, and it matters:**

1. **The live Supabase project.** RLS as *deployed* can differ from the SQL in this repo.
   Several Critical findings below hinge on deployed state. **Before acting on anything in
   §3, run the verification queries in Appendix A against production.** If the deployed
   database already has RLS on `claims`, that finding drops from Critical to a
   schema-drift problem — still real, but different.
2. **Runtime behaviour** — no staging environment, no production logs, no APM, no error
   tracker. There is no telemetry in this codebase at all, so "which pages are slow" is
   literally unanswerable today. That is itself a finding (§9).
3. **Users.** No analytics, no session recordings, no support tickets, no funnel data. The
   UX and Product sections (§6, §7, §11) are therefore **reasoned critique from the code and
   rendered screens, not research.** They are the weakest sections here and should be
   weighted accordingly. I have flagged where I am speculating.
4. **Dependency CVEs** — `npm audit` was not run against a resolved lockfile in a trusted
   network context. Run it; do not take silence here as a clean bill.
5. **Whether any of this is live with real users.** If real PHI is already in production,
   §3's first two findings are an active incident, not a backlog item.

**On the two skills invoked:** the PM roadmap is delivered in §12/§13. `brand-manager` is not
applicable to a code audit — brand work was completed separately in `brand/` and is not
re-litigated here.

**Regulatory note, stated plainly:** this product stores itemised medical expenses, provider
names, dates of service, dependents, and uploaded EOBs. That is health information. Whether
HIPAA applies turns on whether you are a Business Associate of a covered entity — a question
for counsel, not for me. But **state privacy law (CCPA/CPRA, and the newer health-data laws
such as Washington's My Health My Data Act) applies regardless**, and MHMDA has a private
right of action. §3's first finding would be a reportable breach in several of these regimes.
Get a lawyer to scope this before launch, not after.

## 1. Executive Summary

This is a competent, fast-moving solo-founder codebase with a genuinely good product thesis
and a real design point of view. The domain modelling is thoughtful, the
reimbursement-optimiser maths is correct, and the UI is above average for its stage.

It is also **not safe to put in front of real users today.** Three findings are severity
Critical, and two of them are data-exposure issues affecting medical documents. The
single most serious is that uploaded receipts, EOBs and credit-card statements are in a
**public storage bucket with an explicit unauthenticated read policy**. That is not a
hardening gap; that is PHI on the open internet for anyone with a URL.

Beyond security, the engineering-process gap is the thing that will hurt most over the
next year: **zero tests, zero CI, no error tracking, no staging environment.** For an
application that computes tax-advantaged financial projections and stores audit evidence for
the IRS, "we test by clicking around" is not a viable position past the first few hundred
users.

**Verdict: do not launch until §3 CRIT-1, CRIT-2 and HIGH-1 are closed.** Those are
roughly 1–2 days of work. Everything else can be sequenced.

## 3. Security Audit

*(Presented before Architecture because three findings here are launch-blocking.)*

### CRIT-1 — Every uploaded medical document is publicly readable · **Critical**

**[VERIFIED]** `supabase/schema.sql:220-222` creates the bucket as public:

```sql
insert into storage.buckets (id, name, public)
values ('hsa-documents', 'hsa-documents', true)
```

and `supabase/schema.sql:258-261` adds:

```sql
create policy "Public can read hsa-documents"
  on storage.objects for select
  using (bucket_id = 'hsa-documents');
```

**Why it matters.** Postgres RLS policies are **OR-ed, not AND-ed.** The four careful
per-user policies above it (`auth.uid()::text = (storage.foldername(name))[1]`) are
completely nullified by this one. Any object in the bucket is readable by anyone, including
unauthenticated requests. The app compounds this by using `getPublicUrl()` in every upload
path — `src/components/ui/file-upload.tsx:101`, `src/components/dashboard/receipt-scanner.tsx:66`,
`src/app/dashboard/actions.ts:459` — and persisting those permanent public URLs in the
database.

**How it is exploited.** No authentication needed. Paths are
`{user_id}/{folder}/{timestamp}-{filename}`. The `user_id` is a UUIDv4 and not brute-forceable,
so this is not mass-harvestable *by guessing* — but that is the only thing saving you, and it
is not a control. Real leak paths: URLs are emailed in digests, sent to the browser and cached,
leak via `Referer` headers to any third-party script, land in CDN and proxy logs, and are
stored in a database table that any other finding here can expose. **One leaked `doc_urls`
row = permanent, unauthenticated access to that person's medical records.** Revocation is
impossible without moving the object.

**Real-world impact.** Unauthenticated disclosure of health records. Reportable under
several state regimes; MHMDA carries a private right of action. For a pre-revenue product
this is existential, not embarrassing.

**Fix.**
1. `update storage.buckets set public = false where id = 'hsa-documents';`
2. `drop policy "Public can read hsa-documents" on storage.objects;`
3. Replace every `getPublicUrl()` call with `createSignedUrl(path, 60)` issued **server-side**
   after an ownership check.
4. **Store the object path in the database, never the URL.** URLs are ephemeral now; paths
   are the durable key. This means a migration over existing `doc_urls` arrays.
5. Rotate/re-key anything already exposed — assume the existing URLs are compromised.

**Effort:** 1 day (4h for 1–3, the rest is the `doc_urls` migration). **Priority: P0 — blocks launch.**

### CRIT-2 — `claims` and `hsa_administrators` have no RLS · **Critical**

**[VERIFIED]** Across `supabase/schema.sql`, `supabase/migrations/*`, and `Database.sql`, RLS
is enabled on exactly six tables: `expenses`, `profiles`, `dependents`, `expense_templates`,
`hsa_connections`, `plaid_transactions`. The schema defines **eight**. `claims` and
`hsa_administrators` appear in no `enable row level security` statement anywhere in the repo.

**[INFERRED]** Supabase exposes every table in the `public` schema through PostgREST and
grants `anon`/`authenticated` access by default. With RLS disabled, the table is readable and
writable by anyone holding the anon key — **which is public by design and sits in your client
bundle.** This is the single most common Supabase production incident, and Supabase's own
linter flags it as `rls_disabled_in_public`.

**How it is exploited.** No app involvement at all. The attacker signs up, reads
`NEXT_PUBLIC_SUPABASE_ANON_KEY` out of the JS bundle, and issues:

```
GET https://<project>.supabase.co/rest/v1/claims?select=*
  apikey: <anon key>
  Authorization: Bearer <their own JWT>
```

That returns **every user's claims** — amounts, administrators, submission channel, status,
dates. Worse, without RLS there is no write restriction either: `PATCH` or `DELETE` against
other users' claim rows will succeed. `src/lib/claims/submission.ts:118` and `:182` already
delete claims by id; an attacker can do the same to anyone's.

**Fix.** For `claims`:

```sql
alter table public.claims enable row level security;
create policy "own claims select" on public.claims
  for select using (auth.uid() = user_id);
create policy "own claims insert" on public.claims
  for insert with check (auth.uid() = user_id);
create policy "own claims update" on public.claims
  for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy "own claims delete" on public.claims
  for delete using (auth.uid() = user_id);
```

`hsa_administrators` is reference data — enable RLS and add a read-only policy for
`authenticated`; do not grant write.

**Then add a CI check that fails the build if any table in `public` lacks RLS.** This class of
bug recurs every time someone adds a table; a one-time fix does not hold. Query in Appendix A.

**Effort:** 2h including the CI guard. **Priority: P0 — blocks launch.**

### HIGH-1 — SSRF in `POST /api/receipts/scan` · **High**

**[VERIFIED]** `src/app/api/receipts/scan/route.ts:35-45` accepts an arbitrary `imageUrl`
string from the request body and passes it unvalidated to
`extractReceiptData` → `fetchImageAsBase64`, which does a bare
`await fetch(imageUrl)` (`src/lib/receipt-scanner.ts:96`). There is no scheme allowlist, no
host allowlist, no DNS/IP validation, and no redirect limit.

**How it is exploited.** Any authenticated user on the Plus plan (a subscription is a
trivially affordable attack cost) can make your server issue arbitrary outbound GETs:

- `http://169.254.169.254/latest/meta-data/...` — cloud instance metadata.
- `http://localhost:*` / internal VPC addresses — port-scan and reach services that trust the
  network perimeter.
- Blind request forgery against any internal admin endpoint reachable from the function.

Exfiltration is partial rather than blind: the model's `raw_text` field is specified as
"Full text visible on the receipt" and is returned to the caller, so any fetched content the
vision model can read comes back in the response. Redirects also mean an allowlist on the
*initial* host alone is insufficient.

**Fix.** Do not accept a URL at all. The client has just uploaded to your own bucket — accept
the **storage object path** instead, verify the path's first segment equals the caller's
`auth.uid()`, and read the bytes server-side via the Supabase storage API. That closes the
class of bug rather than filtering it. If a URL must be accepted, enforce: `https` only,
exact host match against your Supabase project domain, `redirect: "manual"`, and a response
size cap.

**Effort:** 3h. **Priority: P0 — pairs naturally with CRIT-1's signed-URL work.**

### HIGH-2 — Cron endpoints fail open when `CRON_SECRET` is unset · **High**

**[VERIFIED]** Identical logic in `src/app/api/digest/route.ts:12-17` and
`src/app/api/plaid/sync/route.ts:11-16`:

```ts
const cronSecret = process.env.CRON_SECRET;
if (cronSecret && authHeader !== `Bearer ${cronSecret}`) {
  return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
}
```

**Why it matters.** The guard is conditional on the secret existing. If `CRON_SECRET` is
missing, empty, or typo'd in any environment, **authentication is skipped entirely and the
endpoint is world-callable.** Both routes then construct a `SUPABASE_SERVICE_ROLE_KEY` client,
which bypasses all RLS. This is exactly backwards: a missing secret should fail *closed*.

The blast radius differs per route. `/api/digest` reads every profile and every user's
expenses and sends email — an unauthenticated attacker can trigger mass mail (reputation
damage, Resend quota burn) on demand. `/api/plaid/sync` hits the Plaid API for every
connection, costing money per call and potentially tripping Plaid rate limits.

**Fix.**

```ts
const cronSecret = process.env.CRON_SECRET;
if (!cronSecret) {
  console.error("CRON_SECRET not configured — refusing to run");
  return NextResponse.json({ error: "Not configured" }, { status: 503 });
}
if (authHeader !== `Bearer ${cronSecret}`) { /* 401 */ }
```

Use `crypto.timingSafeEqual` for the comparison. Better still, validate required environment
variables at boot with a Zod schema so the app refuses to start rather than silently
degrading — see ARCH-4.

**Effort:** 1h. **Priority: P0.**

### HIGH-3 — File upload validation is client-side only · **High**

**[VERIFIED]** Size and type are checked in React only —
`src/components/ui/file-upload.tsx:35,62` and `src/components/dashboard/receipt-scanner.tsx:11,27`
(`MAX_FILE_SIZE = 10MB`, `accept="image/*,.pdf,.heic"`). The browser then uploads **directly**
to Supabase storage with the user's JWT. No server code inspects the file.

**Why it matters.** `accept` is a file-picker hint with no enforcement, and the size check is
JavaScript the attacker controls. Any authenticated user can PUT arbitrary content of
arbitrary type into the bucket. Combined with CRIT-1 (bucket is public), **you are operating
unauthenticated file hosting on your own domain** — ideal for malware distribution or phishing
payloads that inherit your domain's reputation.

**Fix.** Set a hard size limit on the bucket itself (Supabase supports per-bucket file size
limits and `allowed_mime_types` — configure both; this is the control that actually binds).
Validate magic bytes server-side rather than trusting `Content-Type`. Strip EXIF from images
— phone photos of receipts carry GPS coordinates of the user's home and doctor's office, which
is a privacy leak nobody has considered here.

**Effort:** 4h. **Priority: P1** (P0 if CRIT-1 is not fixed first).

### MED-1 — Plaid access tokens appear to be stored in plaintext · **Medium**

**[VERIFIED]** `src/app/api/plaid/sync/route.ts:31` selects `plaid_access_token` as an ordinary
column. **[ASSUMPTION]** no application-level encryption — I found no encrypt/decrypt helper
in `src/lib`.

Plaid access tokens are long-lived bank credentials. Anyone with database read access — a
leaked backup, a compromised service-role key, an RLS gap like CRIT-2 — gets durable access
to users' financial institutions. Encrypt at rest with a KMS-managed key (Supabase Vault, or
`pgsodium`), and store only the ciphertext. Rotate existing tokens after fixing.

**Effort:** 1 day. **Priority: P1.**

### MED-2 — No rate limiting anywhere · **Medium**

**[VERIFIED]** No rate-limiting middleware, library, or dependency exists (`grep` for
`ratelimit|upstash|throttle` returns nothing). Unprotected surfaces: auth endpoints
(credential stuffing, user enumeration via timing/response differences), password reset (mail
bombing), and `/api/receipts/scan`, which spends **your Anthropic API budget per call**. A
single Plus subscriber can run your inference bill arbitrarily high.

Add `@upstash/ratelimit` at the middleware layer: strict per-IP on auth, per-user quota on
receipt scanning tied to the plan limits you already model in `src/lib/plans.ts`.
**Effort:** 1 day. **Priority: P1.**

### LOW-1 — Middleware matcher excludes image extensions · **Low**

**[VERIFIED]** `src/middleware.ts:16` excludes `.*\\.(?:svg|png|jpg|jpeg|gif|webp)$` from
session refresh. Any route *ending* in those extensions skips `updateSession`. No such route
exists today, so impact is nil — but it is a trap for whoever adds a dynamic image route

### Things that are correctly done — stated so they are not "fixed" later

- **Stripe webhook signature verification is correct** (`src/app/api/stripe/webhook/route.ts:56-63`)
  — raw body via `req.text()`, `constructEvent`, fail-closed on bad signature. Textbook.
- **No XSS surface** — zero `dangerouslySetInnerHTML` in the codebase; React escaping holds.
- **No SQL injection** — all access goes through the Supabase query builder; no raw SQL

- **`cleanupMfaFactors`** (`src/app/auth/actions.ts:223-250`) correctly re-derives the user

- **CSRF** is adequately handled by Next.js Server Actions' built-in origin checks.

## 1. Architecture Review

The shape is right for the stage: Next.js App Router, Server Actions for mutations, Supabase
for auth/data/storage, Stripe for billing, Vercel for hosting. Nothing here needs to be torn
up. The weaknesses are in the seams.

### ARCH-1 — Schema drift across three sources of truth · **High**

**[VERIFIED]** The schema exists in three places that disagree: `Database.sql` (178 lines, a
dump, **zero RLS statements**), `supabase/schema.sql` (the real thing, with policies), and
`supabase/migrations/*.sql` (13 files, some of which re-declare tables already in
`schema.sql`). Nothing enforces ordering or application; migrations have no timestamps, just
names like `add_coverage_type.sql`.

CRIT-2 is a *direct consequence* of this. When the truth lives in three files, a table gets
added to one and its policies never make it to the others. This will keep happening.

**Fix.** Adopt the Supabase CLI migration workflow (`supabase migration new`), which gives
ordered, timestamped, checksummed migrations. Delete `Database.sql` or clearly mark it
non-authoritative — a file that looks like a schema and silently lacks all security policy is
a trap. Apply migrations in CI, never by hand.
**Effort:** 1 day. **Priority: P0** (it is the root cause of a Critical).

### ARCH-2 — Cron jobs will not survive growth · **High**

**[VERIFIED]** Both background jobs are serial loops inside a single HTTP request.
`/api/plaid/sync` (`route.ts:29-45`) selects **all** connections with no pagination and calls
Plaid once per connection sequentially. `/api/digest` does the same over all subscribed
profiles, issuing a **separate expenses query per user** — a textbook N+1.

At ~50 users with a ~2s Plaid round-trip you are at 100s, already past Vercel's default
function timeout. There is no batching, no concurrency limit, no checkpointing, and **no
retry**: one failure mid-loop and the remaining users are silently skipped until tomorrow.
Users simply do not get their digest and nobody finds out.

**Fix.** Move to a queue (Inngest, Trigger.dev, or QStash — all have usable free tiers). The
cron enqueues one job per user; workers process with concurrency and per-job retry. For the
digest, replace the N+1 with one grouped query. Add a dead-letter queue and alert on it.
**Effort:** 2–3 days. **Priority: P1 — do it before you pass ~100 active users.**

### ARCH-3 — No caching layer of any kind · **Medium**

**[VERIFIED]** No `unstable_cache`, no `revalidate`, no Redis. Every dashboard render
re-queries and re-computes projections from scratch. IRS contribution limits — pure static
reference data — are refetched per request. Fine now; wasteful later.

**Fix.** `revalidate` on static reference data, `unstable_cache` keyed by user id for
derived aggregates, with explicit invalidation in the mutating Server Actions.
**Effort:** 1 day. **Priority: P2.**

### ARCH-4 — Configuration is unvalidated `process.env` access · **Medium**

**[VERIFIED]** 20 distinct env vars read via bare `process.env.X!` with non-null assertions
scattered across route handlers. The `!` tells TypeScript to stop worrying while doing
nothing at runtime — a missing variable becomes a 500 deep inside a request, or worse, the
silent auth bypass in HIGH-2.

**Fix.** One `src/lib/env.ts` with a Zod schema, parsed once at module load. The process
fails to boot on misconfiguration instead of failing open in production.
**Effort:** 3h. **Priority: P1** (it is the structural fix for HIGH-2).

### ARCH-5 — No error handling strategy · **Medium**

**[VERIFIED]** Errors are `console.error`'d and swallowed. `updateProfile` in the Stripe
webhook (`route.ts:24-26`) logs the failure and **returns 200 to Stripe anyway** — so a failed
subscription upgrade is never retried and the user pays without receiving Plus. There are no
`error.tsx` boundaries and no `global-error.tsx`.

**Fix.** Return 500 from the webhook on a database failure so Stripe retries (it will, with
backoff — that is the whole point of the webhook contract). Add route-level `error.tsx`. Wire
Sentry. **Effort:** 1 day. **Priority: P1.**

### Also noted

- **No API versioning** — fine for a first-party-only client; revisit if you ship a mobile app.
- **State management** is local `useState` throughout, no server-state library. At current
  complexity that is the correct call — TanStack Query would be premature. Revisit when two
  components need the same server data.
- **`src/lib/claims/adapters/`** is a genuinely good abstraction — per-administrator claim
  submission behind a common interface. Extend this pattern rather than replacing it.

## 2. Code Quality Review

### CQ-1 — God files · **Medium**

**[VERIFIED]** `src/app/dashboard/actions.ts` is **1,186 lines** containing every Server
Action for expenses, claims, documents, dependents and profile. `expense-form-page.tsx` is
1,168 and `add-expense-dialog.tsx` is 917.

Split `actions.ts` by domain (`actions/expenses.ts`, `actions/claims.ts`, …). The file is a
merge-conflict magnet and nobody can hold it in their head.
**Effort:** 1 day, mechanical and low-risk. **Priority: P2.**

### CQ-2 — The expense form exists twice · **Medium**

**[VERIFIED]** `add-expense-dialog.tsx` (917 lines, 77 domain-field references) and
`expense-form-page.tsx` (1,168 lines, 110 references) implement the same expense form — one
in a dialog, one as a page. Two copies of the same validation and submission logic.

This is the highest-value refactor in the codebase: **every field change, every validation
rule, every eligibility tweak has to be made twice, and one of them will be forgotten.** That
is not hypothetical; it is how the two files already drifted to different field counts.

Extract one `<ExpenseForm>` taking a `mode` prop; keep dialog and page as thin shells.
**Effort:** 2 days. **Priority: P1** — pays for itself within a month.

### CQ-3 — Zero input validation on Server Actions · **High**

**[VERIFIED]** `zod@4.3.6` is a dependency and is used for *form* validation via
`@hookform/resolvers`, but Server Actions parse `FormData` and trust it. Server Actions are
public HTTP endpoints — client-side validation is a UX affordance, not a control.

Consequences today are data-integrity rather than auth (RLS still scopes rows *if* enabled —
see CRIT-2): negative amounts, 10MB strings in a `text` column, dates in year 9999, invalid
enum values landing in the database.

**Fix.** A Zod schema per action, parsed first, typed output thereafter. `src/lib/types.ts`
already defines the enums — reuse them.
**Effort:** 2 days. **Priority: P1.**

### CQ-4 — Floating-point money · **Medium**

**[INFERRED]** Amounts flow through JS `number`. `0.1 + 0.2 !== 0.3` — over a year of
expenses, totals and tax summaries drift by cents. For a product whose entire promise is
audit-ready IRS records, "close enough" is the wrong answer.

Store money as integer cents (`bigint`) or Postgres `numeric`, and convert only at the
display boundary. This gets *much* more expensive to change later, so do it early.
**Effort:** 2 days now, 2 weeks after launch. **Priority: P1.**

### CQ-5 — Dead code and an unused dependency · **Low**

`src/components/dashboard/scenario-comparison.tsx:73` has an unused `e` binding (flagged by
lint). `@react-pdf/renderer` is a dependency but I found no import of it — if PDF export was
abandoned, drop it; it is a heavy package.

### Credit where due

`src/lib/types.ts` (426 lines) is well-structured: domain enums, `ELIGIBLE_EXPENSES`, and
audit-readiness logic in one place. `isAuditReady` and `calculateExpectedReturn` are pure
functions — **which means they are trivially testable, and there is not one test for them.**
That is the clearest illustration of the testing gap in this codebase: the hard work of making
the code testable is already done, and nobody took the last step.

## 4. Performance Review

### PERF-1 — Stripe webhook does a sequential scan on every event · **High**

**[VERIFIED]** `updateProfile` filters `.eq("stripe_customer_id", customerId)` — and there is
**no index on `profiles.stripe_customer_id`** anywhere in the repo. Every webhook (checkout,
subscription update/delete, payment failure) full-scans the profiles table. Stripe times out
webhooks at 10s and retries; past ~100k profiles you enter a retry loop that manifests as
users paying and not being upgraded.

```sql
create index concurrently if not exists idx_profiles_stripe_customer_id
  on public.profiles (stripe_customer_id) where stripe_customer_id is not null;
```

**Effort:** 5 minutes. **Priority: P1 — best effort-to-impact ratio in this document.**

### PERF-2 — `claims` has no index at all · **Medium**

**[VERIFIED]** No `create index` statement mentions `claims`. Every claims query is a scan.
Add `idx_claims_user_id on public.claims (user_id)` and a composite
`(user_id, status)` for the filtered list view. **Effort:** 10 min. **Priority: P1.**

### PERF-3 — Digest N+1 · **High**

Covered in ARCH-2. One query per subscriber. At 10k subscribers that is 10,001 round-trips in
a single request. **Priority: P1.**

### PERF-4 — `select("*")` everywhere · **Low**

**[VERIFIED]** e.g. `digest/route.ts:53` (`profiles`) and `:76` (`expenses`). Pulls every
column including large `doc_urls` arrays when only a handful of fields are used. Wasteful over
the wire and blocks index-only scans. Enumerate columns. **Effort:** 2h. **Priority: P2.**

### PERF-5 — Unoptimised logo asset · **Low**

`public/logo.png` is a 512×512 PNG rendered at 36px. Next's `<Image>` handles resizing, but
shipping an SVG (already at `public/logo.svg`) would be smaller and sharper. Minor.

**Not assessable without telemetry:** bundle size, LCP/CLS, actual slow pages. There is no
RUM and no Lighthouse budget. Add both before optimising anything by intuition — §9.

## 5. Database Review

**Good:** UUID PKs, `on delete cascade` from `auth.users`, sensible column types, reasonable
core indexes on `expenses` (`user_id`, `date_of_service`, `account_type`, `reimbursed`,
`tax_year`).

**Problems:**

| # | Finding | Severity |
|---|---|---|
| DB-1 | `claims`, `hsa_administrators` lack RLS (CRIT-2) | **Critical** |
| DB-2 | Three conflicting schema sources (ARCH-1) | **High** |
| DB-3 | No index on `profiles.stripe_customer_id` (PERF-1) | High |
| DB-4 | No index on `claims.user_id` (PERF-2) | Medium |
| DB-5 | Money stored as float (CQ-4) | Medium |
| DB-6 | No `updated_at` triggers — columns exist but nothing maintains them | Medium |
| DB-7 | No soft deletes; `on delete cascade` means deleting a dependent silently destroys linked expense history the IRS may require for 7 years | **High** |
| DB-8 | No audit trail — no record of who changed an expense amount or when | High |
| DB-9 | No documented backup/PITR posture or restore drill | **High** |
| DB-10 | No archiving strategy for the 7-year retention the product promises | Medium |

**DB-7 and DB-8 deserve attention beyond their line items.** The product's core promise is
*audit-ready documentation*. A hard delete that cascades away evidence, with no history of
who changed what, is directly at odds with that promise. If a user is audited and their
records were silently cascaded, the product failed at the one job it advertises. Add
`deleted_at` soft deletes and an append-only `expense_history` table before launch, not after.

**DB-9:** confirm Supabase PITR is enabled for your plan tier, and **actually perform a
restore into a scratch project.** An untested backup is a belief, not a control.

## 9. Reliability & DevOps Review

This is the weakest area of the project and the scores reflect it.

**[VERIFIED] What does not exist:** no `.github/workflows` (no CI at all), no tests, no error
tracking, no APM, no uptime monitoring, no alerting, no structured logging, no health-check
endpoint, no feature flags, no staging environment, no documented rollback, no runbook, no
disaster-recovery plan, no dependency scanning.

**What exists:** Vercel's default git-push deploys and instant rollback, `vercel.json` with one
cron, and `console.log`. Vercel's rollback is genuinely good and is doing a lot of unearned
work for you here.

**The consequence is concrete, not abstract:** today, if the Stripe webhook starts failing,
**nobody finds out.** The error is `console.error`'d into Vercel logs that no one reads, 200
is returned to Stripe so it never retries, and the first signal is a support email from a
customer who paid and did not get Plus. Same for a Plaid sync that dies mid-loop.

**Minimum viable ops, in priority order:**

1. **Sentry** — 30 minutes, and it converts invisible failures into alerts. Do this first.
2. **CI on every PR** — `tsc --noEmit`, `eslint`, `next build`. The repo already passes all
   three, so this costs nothing and prevents regression. ~2h.
3. **RLS guard in CI** — fail the build if any `public` table lacks RLS (Appendix A).
4. **Uptime + cron monitoring** — a dead cron is currently undetectable. Healthchecks.io is free.
5. **Staging environment** on a separate Supabase project. You are currently testing schema
   changes in production.
6. **Secret rotation runbook.** Note that `SUPABASE_SERVICE_ROLE_KEY` is used in four places;
   if it leaks, everything is exposed regardless of RLS.

**Effort:** 1 week total for all six. **Priority: P0 for 1–3.**

## 10. Testing Review

**[VERIFIED] There are zero tests.** No test files, no test runner, no testing dependency in
`package.json`. Coverage is 0%.

For a product that computes compounding projections and tax positions people act on, this is
the finding most likely to produce a *silent* failure — a wrong number that looks plausible,
ships, and is trusted. Security holes get found and fixed; a subtly wrong `calculateExpectedReturn`
just quietly misinforms people about their retirement for years.

**Do not chase coverage. Test in this order:**

1. **Pure financial logic first** — `isAuditReady`, `calculateExpectedReturn`,
   `use-savings-projection.ts`, the optimiser's `amount * (1 + rate) ^ years`. These are pure
   functions with zero setup cost, they encode the product's core claims, and they are the
   highest-consequence code in the repo. Vitest, one afternoon, and the single best testing
   investment available to you.
2. **RLS policy tests** — assert user A cannot read user B's rows, per table. This is the
   regression test for CRIT-2 and it is what stops it recurring.
3. **Webhook handling** — signature rejection, each event type, database-failure path.
4. **E2E on two paths only** — signup→onboard→add expense, and upgrade→Plus unlocked.
   Playwright. Keep it to the money paths; broad E2E suites rot.

Skip performance and load testing for now — you do not have the traffic to justify it, and
the cron architecture (ARCH-2) needs replacing before load numbers mean anything.

**Effort:** 1 week for 1–3, 3 days for 4. **Priority: P0 for step 1.**

## 6. User Experience Review

**Weight this section lightly.** I have no analytics, no session recordings and no user
interviews. This is critique from reading the code and rendered screens. Every claim below is
a **hypothesis to validate**, not a finding — the difference matters, and I would not act on
the speculative ones without evidence.

**What is genuinely good:** the visual craft is well above average for this stage. A coherent
design system in `globals.css`, a real philosophy in `docs/design-philosophy.md`, dark mode
throughout, and **171 responsive breakpoint uses** — mobile was designed for, not bolted on.
The landing page is strong.

### UX-1 — No loading states anywhere · **High** · [VERIFIED]

Zero `loading.tsx` files, zero `<Suspense>` boundaries, and **zero `isLoading`/`isPending`/
`isSubmitting` state in the entire codebase.** On a slow connection the dashboard shows
nothing and then everything; a submitted form gives no feedback at all.

The specific risk: a user taps "Save expense", sees nothing happen, and taps again.
Without an idempotency guard that is a duplicate expense — which corrupts the audit trail this
product exists to protect.

**Fix.** `loading.tsx` per route with skeletons matching the real layout; `useFormStatus` to
disable submit buttons and show progress. **Effort:** 2 days. **Priority: P1.**

### UX-2 — Only 2 `<label>` elements in the entire app · **High** · [VERIFIED]

Against 34 `aria-*` attributes, 8 `role=`, 20 `alt=` and a skip-link — someone clearly thought
about accessibility in places. But **2 labels across every form in a forms-heavy product**
means inputs are largely label-less or rely on placeholders.

Placeholders are not labels: they vanish on focus, fail screen readers, and fail WCAG 1.3.1
and 3.3.2. For a product handling medical and financial data — likely to be used by older and
disabled users, and plausibly subject to accessibility procurement requirements — this is a
real exclusion, not a lint nit.

**Fix.** Audit every input; the shadcn `<Label>` component is already a dependency. Run axe.
**Effort:** 2 days. **Priority: P1.**

### UX-3 — Empty states are largely missing · **Medium** · [VERIFIED]

Only two empty-state strings exist across all dashboard components. The one that does exist
is good ("No unreimbursed expenses yet. Track expenses to see reimbursement strategies." —
explains *and* directs). The rest of the dashboard on day one is presumably blank panels.

The empty state **is** the first-run experience and it is where activation is won or lost.
Every list, chart and panel needs one with a single clear next action.
**Effort:** 2 days. **Priority: P1.**

### UX-4 — Hypotheses I could not test

Flagged as speculation:

- The 1,168-line expense form suggests a long single-screen form. If a user must fill 15
  fields to log one copay, that is likely the biggest drop-off in the product — but I am
  inferring from line count, which is weak evidence. **Instrument it before redesigning.**
- Onboarding is a 622-line dialog. README says "guided 3-step onboarding". Whether it teaches
  the *core insight* (don't reimburse yourself yet) or just collects settings, I cannot tell
  from the code. If it is settings collection, that is a missed opportunity — the insight is
  the product.
- No search anywhere in the dashboard. Fine at 20 expenses, painful at 500.

## 7. Customer Experience Review

**Same caveat — no support tickets, no churn data, no session data.**

The central CX problem is structural and I am confident in it: **the product's value is
invisible for years.** A user logs expenses now and gets reimbursed in 2046. There is no
feedback loop, and products without feedback loops get abandoned.

The reimbursement optimiser is the fix and it is underused. It should be the *home screen* —
"your unreimbursed pile is worth $X today, $Y if you wait" — recomputed and surfaced on every
visit. That single number is the entire reason to come back. Today it is a component on a
dashboard among others.

**Also missing:** any help documentation, any in-app support channel, any feedback mechanism,
any changelog. For a product asking users to trust it with 7 years of IRS evidence, trust
signals are thin — the privacy page (496 lines) is good and substantive, but there is no
security page, no data-handling explanation, no "what happens if you shut down" answer. That
last one is a real objection for a solo-founder product asking for a decades-long commitment,
and it deserves a real answer (data export, in writing).

**Recommendation:** add CSV/PDF export prominently and market it as *"your data leaves
whenever you want."* It converts the biggest adoption objection into a trust signal, and the
export code largely exists already.

## 8. Feature Gap Analysis

**High-value, close to existing code:**

1. **Year-end tax package** — one PDF with every reimbursed expense, receipts attached,
   audit-readiness per line. `@react-pdf/renderer` is already installed and unused. This is
   the highest-value feature not yet built, it is directly monetisable, and it is the natural
   annual re-engagement moment.
2. **"What should I reimburse?" advisor** — you compute growth potential already; turn it
   into a ranked recommendation with a reason per line.
3. **Contribution-limit tracking with alerts** — you have the IRS limits; alert at 80%/100%
   and on over-contribution, which carries a real 6% excise penalty. High user value,
   low effort.
4. **Receipt-to-expense auto-match** — Plaid transactions and scanned receipts both exist;
   matching them is the obvious next step and removes most manual entry.
5. **Bulk import** — CSV from an existing HSA administrator. Today a switcher must hand-enter
   years of history, which is an adoption wall.

**Differentiating and defensible:**

6. **Audit Mode** — generate exactly the IRS-requested document set for a date range. Nobody
   does this well, and it is the strongest possible expression of the brand promise.
7. **Spouse/family shared access** — HSAs are household, the app is single-user. Requires real
   authorisation work (do it *after* RLS is fixed, not before).
8. **Document retention automation** — you promise 7-year retention; automate expiry warnings.

**Do not build yet:** mobile app, more AI features, collaboration. Fix the foundation first.
Every one of these multiplies the surface area of the problems in §3 and §10.

## 11. Product Review

**The thesis is genuinely good** and better than most in the category: HSAs are the most
tax-advantaged account in the US code and almost nobody uses the
pay-out-of-pocket-and-defer-reimbursement strategy. A tool that makes that strategy tractable
has a real reason to exist.

**The hard product problems, honestly stated:**

1. **The market is smaller than it looks.** The addressable user is someone who maxes an HSA,
   invests it, *and* pays medical costs out of pocket. That is a thin slice — affluent,
   financially sophisticated, already spreadsheet-inclined. The good news: they pay for tools
   and they are reachable. The bad news: "power user" is not a growth strategy on its own.
2. **Your competitor is a spreadsheet**, and it is free, flexible, and already in use. You
   must beat it on something structural — receipt storage, audit packaging, automated
   matching — not on charts.
3. **Value realisation is measured in decades** (see §7). This is the core retention risk.
4. **Trust is the adoption barrier**, and it is directly undermined by §3. A single disclosure
   incident ends this product. The security findings are not just engineering debt; they are
   the product's primary business risk.

**Monetisation.** The free/Plus split looks reasonable, though gating *receipt scanning* —
the feature that most reduces entry friction — behind Plus may suppress the activation that
drives upgrades. Worth an experiment: give free users a small monthly scan quota. The
strongest paid hook is the year-end tax package (#1 above): annual, high-value, obviously
worth money at exactly the moment users feel the pain.

## Appendix A — Verification queries

Run against **production** before acting on §3. These confirm deployed state, which may differ
from the repo.

```sql
-- 1. Which public tables lack RLS? Expect zero rows. Also use this as the CI guard.
select c.relname as table_without_rls
from pg_class c join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relkind = 'r' and not c.relrowsecurity;

-- 2. Is the document bucket public? Expect false.
select id, public from storage.buckets where id = 'hsa-documents';

-- 3. Any storage policy granting unconditional read?
select policyname, qual from pg_policies
where schemaname = 'storage' and tablename = 'objects';

-- 4. Confirm the Stripe lookup index exists.
select indexname from pg_indexes
where tablename = 'profiles' and indexdef ilike '%stripe_customer_id%';
```
